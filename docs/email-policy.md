# 사용자 이메일 정책

## 목적

사용자 이메일을 계정 식별자로 일관되게 처리하고, 대소문자 차이로 동일 사용자가 중복 가입하거나 로그인하지 못하는 문제를 방지한다.

## 정규화 규칙

이메일은 다음 순서로 정규화한다.

1. 문자열 앞뒤 공백을 제거한다.
2. 전체 이메일을 소문자로 변환한다.
3. 정규화된 이메일을 가입, 수정, 로그인, 인증 메일 재전송에 사용한다.

예를 들어 다음 입력은 모두 동일한 이메일로 취급한다.

```text
 user@example.com
USER@EXAMPLE.COM
User@Example.Com
```

정규화된 값은 다음과 같이 저장된다.

```text
user@example.com
```

## API 동작 규칙

### 가입

- 이메일을 정규화한 뒤 저장한다.
- 정규화 결과가 기존 사용자와 중복되면 `409 Conflict`를 반환한다.
- 이메일 중복 여부는 애플리케이션 검사만으로 판단하지 않고 PostgreSQL unique 인덱스로 최종 보장한다.

### 사용자 정보 수정

- 이메일이 포함된 경우 정규화한 뒤 저장한다.
- 정규화 결과가 기존 이메일과 같으면 이메일 변경으로 보지 않는다.
- 대소문자만 변경된 요청은 이메일 재인증을 발생시키지 않는다.
- 실제 이메일이 변경되면 `email_verified`를 `false`로 변경하고 새 인증 토큰을 발급한다.

### 로그인

- 요청 이메일을 정규화한다.
- DB 조회에서도 `lower(email) = lower($1)` 조건을 사용해 대소문자를 무시한다.
- 이메일 미인증 사용자는 로그인 성공으로 처리하지 않는다.

### 인증 메일 재전송

- 요청 이메일을 정규화한다.
- 대소문자가 다른 이메일로 요청해도 동일 사용자를 찾는다.
- 이미 인증된 계정은 `이미 인증됨` 상태를 반환한다.

## PostgreSQL 제약 조건

`auth.users.email`에는 소문자 기준 unique 인덱스가 있어야 한다.

```sql
CREATE UNIQUE INDEX users_email_lower_unique
ON auth.users (lower(email));
```

이 인덱스는 다음 두 값의 중복을 차단한다.

```text
user@example.com
USER@example.com
```

`lower(email)` 인덱스는 비교와 중복 방지만 담당하며, 이미 저장된 이메일 값을 자동으로 소문자로 변경하지 않는다. 따라서 애플리케이션과 Repository의 저장 경로에서도 이메일을 정규화해야 한다.

정확한 문자열 비교용 `UNIQUE(email)` 제약은 `lower(email)` unique 인덱스와 정책상 중복되므로 함께 유지하지 않는다. 단, 제거 전에는 해당 환경의 중복 데이터와 제약 조건을 먼저 확인한다.

## 현재 백엔드 적용 위치

- `src/users/users.input.ts`
  - 요청 이메일의 공백 제거와 소문자 변환
- `src/users/users.repository.ts`
  - 가입·수정 시 `lower()`를 적용한 저장
  - 이메일 조회 시 `lower(email) = lower($1)` 사용
- `src/users/users.service.ts`
  - 이메일 변경 여부 판단
  - 이메일 변경 시 재인증 처리

## 테스트 기준

다음 동작을 회귀 테스트로 유지한다.

- 대문자 이메일 가입 요청이 소문자로 저장되는지 확인
- 대문자 이메일 수정 요청이 소문자로 저장되는지 확인
- 대소문자만 다른 이메일로 로그인 가능한지 확인
- 대소문자만 다른 이메일로 인증 메일 재전송이 가능한지 확인
- 동일 이메일 중복 가입 시 `409 Conflict`가 반환되는지 확인
- 이메일이 실제로 변경된 경우에만 재인증이 요구되는지 확인
