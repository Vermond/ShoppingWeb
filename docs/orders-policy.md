# 주문 정책

## API

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| `POST` | `/api/orders` | 현재 사용자의 장바구니로 주문 생성 |
| `GET` | `/api/orders` | 현재 사용자의 주문 목록 조회 |
| `GET` | `/api/orders/:id` | 현재 사용자의 주문 상세 조회 |
| `POST` | `/api/orders/:id/cancel` | 현재 사용자의 주문 취소 |

모든 주문 API는 Access Token Cookie 인증이 필요하다. Access Token Guard에서 활성 계정이면서 이메일 인증을 완료한 사용자만 통과시킨다.

## 주문 생성

주문 생성 요청은 다음 형식을 사용한다.

```json
{
  "address_id": "배송지 UUID",
  "delivery_request": "문 앞에 놓아주세요"
}
```

`address_id`는 요청한 사용자 소유의 `auth.user_addresses` 주소여야 한다. 배송지 정보는 주문 생성 시 `sales.order_addresses`에 복사해 저장한다. 이후 원본 배송지가 변경되거나 삭제되어도 기존 주문의 배송지는 변경되지 않는다.

주문 생성 트랜잭션에서 다음을 다시 확인한다.

- 장바구니가 비어 있지 않은지
- 상품이 `active` 상태인지
- 요청 수량이 `max_order_quantity` 이하인지
- 요청 수량이 현재 재고 이하인지
- 주문 당시 상품 가격과 수량으로 계산한 금액

상품 행은 `FOR UPDATE`로 잠근 뒤 재고를 차감한다. 검증·주문 생성·주문 항목 저장·배송지 스냅샷 저장·재고 차감·장바구니 비우기는 하나의 트랜잭션으로 처리한다. 중간에 실패하면 전체 변경을 롤백한다.

금액은 PostgreSQL `numeric(12,2)`의 정밀도를 유지하기 위해 `Decimal`로 계산하고 API에서는 소수 둘째 자리까지의 문자열로 반환한다.

## 목업 결제

현재 결제 서비스는 `MockPaymentService`다. 결제 요청을 외부 결제사로 전송하지 않고 즉시 승인한 뒤 주문 상태를 `paid`로 저장한다. 실제 결제 연동 시에는 이 서비스만 실제 결제 어댑터로 교체할 수 있도록 분리했다.

현재 결제 테이블이나 결제 식별자는 저장하지 않는다. 따라서 실제 결제 연동 전에는 결제 상태·결제 승인 ID·결제 실패 보상 처리 등을 별도로 추가해야 한다.

## 주문 취소

현재 구현에서는 `paid` 상태의 주문만 취소할 수 있다. `shipped`, `completed` 상태는 취소할 수 없다. 이미 `cancelled` 상태인 주문에 같은 취소 요청을 다시 보내면 기존 취소 주문을 반환한다.

결제 완료 주문을 취소하면 주문 상태를 `cancelled`로 변경하고 주문 당시 수량만큼 상품 재고를 복원한다. 주문 상태 변경과 재고 복원은 같은 트랜잭션에서 처리한다.

현재 목업 결제에서는 주문 생성이 즉시 `paid`가 되므로 생성 직후 취소가 가능하다. 환불 처리는 목업으로도 별도 수행하지 않으며, 실제 결제 연동 단계에서 결제 취소·환불 성공 여부를 주문 상태 변경 조건에 포함해야 한다.

## 응답 금액

주문 상세의 `total_amount`, `unit_price`, `subtotal`은 다음과 같이 문자열로 반환한다.

```json
{
  "total_amount": "25800.00",
  "unit_price": "12900.00",
  "subtotal": "25800.00"
}
```
